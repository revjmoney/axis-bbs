What the BBS is, what it does and what you need to run one.

Axis Micro BBS Firmware is a real, old-school bulletin board system that you call with a telnet terminal. It is written from scratch in C++ and runs entirely on the ESP32 "Cheap Yellow Display" (CYD, model ESP32-2432S028R): a 2.8 inch 320x240 touchscreen board with 4 MB of flash and no PSRAM. There is no PC behind it. The little board answers the calls, draws the ANSI screens, keeps the users and messages, serves the files over ZMODEM, and even runs real DOS door games like Legend of the Red Dragon on an 8086 emulator.

The live board it was built for is AXIS UNDERGROUND CNC, run by Rev. J. Money, the maker of RotatoCAM. The software is the same for anyone who flashes it.

What it does
  • Telnet BBS on port 23 (configurable), 80x25 ANSI with CP437 art, tested with SyncTERM.
  • Two complete looks: Axis (drippy orange) and Oblivion (grey and cyan, in the style of Oblivion/2), switchable with one tap. Sysop art packs drop in from the SD card.
  • Accounts with a new user application, validation, security levels, permissions, a time limit and an idle logoff.
  • File areas on a microSD card with ZMODEM, XMODEM and XMODEM-1K downloads and uploads, an upload checker, archive listings, search, new files and a download ratio.
  • Message areas with quoting and taglines, a new message scan, and private email.
  • Oneliners, rumors, a BBS list, top ten, a voting booth, last callers and a bulletin.
  • Several callers per board, and several boards on one LAN joined into one BBS: teleconference, node messages, broadcasts and live split-screen chat between callers.
  • Real DOS doors (LORD 4.07, BBS Black Jack) through DOOR.SYS and a FOSSIL driver, plus built-in doors: an ANSI pack viewer with ANSI movies, and a password-locked DOS prompt.
  • A touch sysop console on the board itself: activity screen, node details with KICK, user validation, settings, logs, SD formatting, and a local login on the 2.8 inch screen.

Flash the firmware with PlatformIO and join WiFi on the touchscreen.

If you bought a ready-to-plug-in unit, the firmware is already installed: skip to WiFi. To flash your own board, start with flashing.

Flashing the firmware

The firmware builds with PlatformIO. Install it (the VS Code extension or the command line), clone the repository, plug the CYD in over USB, find its COM port, and run:

git clone https://github.com/revjmoney/axis-bbs.git
cd axis-bbs
pio run -e cyd -t upload --upload-port COM5

Use your own port name (COM5 on Windows, something like /dev/ttyUSB0 on Linux). The cyd environment is the default, so pio run -t upload does the same. Other environments are covered under headless nodes and building.

NoteYour users, settings and logs live in the internal LittleFS partition. Flashing new firmware over the top keeps them: the partition table keeps LittleFS at the same place on every release.
WiFi on the touchscreen

On first boot (or whenever no saved network is in range) the board opens a touch WiFi picker. It lists the networks it can hear, strongest first. Tap yours, type the password on the on-screen keyboard (it is masked; SHOW reveals it) and press OK. HIDDEN lets you type a network name that does not broadcast, RESCAN looks again and MORE pages the list. The network is saved only after the join works, and the board remembers up to five networks.

The 6-digit setup PIN, the telnet wizard and your sysop account.

Once it is on your network, the board asks how you want to set the BBS up: ON THIS SCREEN or OVER TELNET.

  • Over telnet is the easy way: the screen shows telnet axis.local, the board's address, and a 6-digit setup PIN. Call in from a computer on the same network, type the PIN, and answer the wizard. Anyone who calls before setup is done only sees "This BBS is being set up" and a PIN prompt.
  • On this screen is reserved for an on-screen wizard. In version 0.3 it only says the on-screen setup is coming in a later build and offers a way back, so use telnet.

You can also make any caller a sysop later; see sysop promotion. On the board, the LOCAL button logs you in as the sysop without a password.

Terminals, axis.local, and opening the board to the internet.

Callers reach the BBS with a telnet terminal. SyncTERM is the reference terminal and everything is tested with it; other ANSI BBS terminals work too. Set the terminal to 80x25 with a CP437 (IBM PC) font so the block art lines up.

Dialing on your own network

On the same LAN the board announces itself over mDNS, so callers dial the board name with .local:

syncterm telnet://axis.local
telnet axis.local 23

If a computer cannot resolve .local names, use the board's IP address instead. The board shows it on its activity screen ticker and in SYSTEM on the sysop menu, and callers see it with I (system info).

With a cluster, callers always dial the main board. When every node on the main is busy, it passes the new caller through to the lowest free node on another board, so one address serves the whole system. See multinode and clustering.

Opening it to the internet

The BBS was built for the LAN first. To let callers in from outside, forward a port on your home router to the main board:

  1. Give the main board a fixed address. In your router's DHCP settings, make a DHCP reservation for the board's MAC address so its LAN IP never changes.
  2. Forward a TCP port to that address, port 23 (or whatever telnet_port is). You can forward outside port 23 straight through, or use a different outside port such as 2323 and point it at the board's port 23. A non-standard outside port cuts down on bot traffic.
  3. Tell callers the address. Put your public hostname in public_host; the Oblivion look's front door shows it as the dial address. A changing home IP can be followed with the optional dynamic DNS extra (No-IP, asked by the wizard, or GoDaddy).
Heads upOnly the main board needs a forward. Other boards in the cluster are reached through it.

Only one session can be in a door or a file transfer per board at a time. If a second caller on the same board asks, they are told the door is busy and to try again (or call back, since they may land on a free node).

Splash, front door, password, bulletin, oneliners, menu.

Every call walks through the same steps. Each one can be skipped or customized.

  1. The RotatoCAM splash. An animated ANSI splash types in like a 9600 baud modem, then plays about five seconds of moving parts (a light sweep on the logo, a tool path, spinning flutes, chips) and a colour-cycling marquee. Any key skips it. Turn it off with login_splash=0.
  2. The front door. In the Axis look: the drippy AXIS login screen with THE BOARD and THE SYSTEM boxes, then a Handle: prompt. In the Oblivion look: the matrix with a lightbar over Login, Apply, Who's Online and Goodbye (arrow keys move it, Enter picks, or press the letter).
  3. Handle and password. A known handle asks for its password (masked, three tries, then the call ends). After a wrong password the board ignores typing for 2 seconds, then 4, so guessing is slow. An unknown handle is offered the new user application.
  4. The bulletin. If the theme folder has a BULLETIN.ANS, it shows once, then any key goes on.
  5. Oneliners. The newest ten oneliners, and the offer to add one (up to 60 characters).
  6. The main menu. With "You have N new mail" under it if private mail is waiting, and a random rumor.

Validated callers go straight to the menu. A caller whose application is waiting gets the PENDING VERIFICATION screen and a short menu instead: Status, Credits, Goodbye. A denied caller is told so and disconnected.

Two timers run on every call: the idle logoff (idle_minutes, default 5) and the call time limit (daily_minutes, default 60). See time limits.

The Axis and Oblivion looks, and the THEME button.

The whole board wears one of two looks, set by theme. Every caller on every node sees the same one.

Looktheme=Style
Axis (default)axisBlack, grey, orange and white. Big half-block drippy titles with acid drips, headings that fade white to grey, keys in orange inside grey brackets, orange frames.
OblivionoblivionDark grey and cyan in the style of the stock Oblivion/2 screens (drawn from scratch, no O/2 art copied): the matrix front door with a lightbar, spaced title bars, double-line boxes, a boxed two-column main menu and the O/2 bracket prompt [Main Menu][Node 1] :.
Switching the look
  • On the board: tap the activity screen, open BBS SETUP and tap THEME. Each tap flips between the two.
  • On the serial console: @SET theme=oblivion or @SET theme=axis.
  • In /axis.ini: theme=oblivion. Any value other than oblivion means axis.

The main board sends the change to every board in the cluster at once. The next screen each caller gets is in the new look.

Put ANSI screens on the main board's SD card under /sd/themes/<theme>/ (so /sd/themes/oblivion/ or /sd/themes/axis/). Boards without a card fetch them from the main over the link, so every node looks the same.

Areas on the SD card, FILES.BBS and browsing.

The file areas live on the main board's microSD card. Press F at the main menu. Without a card the file areas say they are offline; boards in a cluster without a card browse and transfer the main's files over the link.

Areas and the SD card layout

Each area is a folder: /sd/files/<id>/, where the id comes from the area's setting. The board makes the folders for every listed area when it starts. Inside each folder, an optional FILES.BBS gives the descriptions, one file per line: the file name, a space, then the description.

/sd/files/gcode/FILES.BBS
SPIRAL.NC     Spiral flute toolpath for a 4th axis, 1/4 inch end mill
LOGO.NC       AXIS logo, 2D pocket, 3 mm deep

FILES.BBS is optional: files in the folder without a line still show, after the listed ones, with no description.

Areas are set with areaN=id|name, areaN=id|name|level or areaN=id|name|level|m (m: mirrored onto two SD cards when the cluster has them; see SD card clustering). They are sorted by the number N, and a repeated number replaces the earlier one, so @SET area0=new|New Uploads adds an area at the top. The optional level is the lowest security level that can see the area at all; callers below it never see it (the sysop sees everything). If no areaN lines are set, the default list is used:

Archive listings, search every area, new files.

I shows a file's name, size, area and description. For an archive it also lists what is inside, read straight from the archive headers: every entry with its size, packed size, method, date and CRC (the first 40 of a long pack, then the count), plus FILE_ID.DIZ when there is one. Supported formats: ZIP, RAR (1.5 to 4), RAR 5, ARJ, TAR and GZIP. Info is open to everyone, even before they have earned downloads.

Search and new files

/ at the area list searches the names and descriptions in every area you can see, case-insensitive, and groups the hits by area (up to 60 shown). N lists every file that landed since your previous call, by the file dates on the card; on a first call it shows the last seven days.

ZMODEM and XMODEM, the upload checker, the download gate and ratio.

Pick D, type the file name, then the protocol: Z ZMODEM, X XMODEM (CRC) or K XMODEM-1K. A themed window shows the file, size, protocol and an estimated time; start your terminal's download and press Ctrl-X five times to cancel. A second window reports the bytes moved and the speed. ZMODEM is by far the fastest (around 247 KB/s measured on the board over WiFi), and the CYD shows a live progress window during the transfer.

For U, describe the file in one line (Enter cancels), pick the protocol and start your terminal's upload. ZMODEM sends the file name; for XMODEM the board asks what to save it as. Uploads get a clean name, never overwrite an existing file, and land in one piece (written to a temporary file, then renamed). The description goes into the area's FILES.BBS.

The upload processor

Every ZIP upload is checked before it is accepted: the board unpacks it, tests every entry's CRC-32, adds or replaces an AXISBBS.NFO (board name, telnet address, location, software, rotatocam.com and jmscnc.com) and writes a clean standard ZIP in place. Damaged, password-protected and old-method (shrink or implode) ZIPs are rejected and removed with the reason shown. Other file types are kept as uploaded. The caller watches a PROCESSING UPLOAD window with a live bar, and the description reaches FILES.BBS only after the check passes.

The download gate and ratio

Downloads are earned. A new caller can browse the lists and use Info, but Download and View wait until they have uploaded something. The sysop can wave this for one caller with FREE DL (on the CYD under CALLER, ACCESS, or with L in the telnet user editor).

On top of that you can set a ratio: with ratio=3 and free_kb=512, a caller can download up to three times the bytes they have uploaded, plus a 512 KB allowance. ratio=0 (the default) means no ratio. FREE DL skips the ratio too. Upload and download bytes are counted on every account and shown in the user editor and on the node detail screen.

Reading, posting, quoting, taglines and the new scan.

Press M for the message areas. The main board keeps one message file per area (on the SD card, or internal flash without one); other boards read and post over the link, so every caller sees the same messages.

Areas

Areas are set with msgareaN=id|name or msgareaN=id|name|level, with the same numbering and level rules as file areas. Several callers per board, and boards that join into one BBS.

One board takes several callers at once, and several boards on one LAN join into one BBS with shared users, settings, files, messages and lists. Each caller slot is a node.

Sessions per board

sessions sets how many callers a board takes at once: 1 to 4, default 2 on a CYD (a headless node defaults to 3). Each session is its own node number; the activity screen shows them as, for example, node 1+2. Doors and file transfers share one memory slot per board, so only one session per board can be in a door or a transfer at a time. Everything else (menus, messages, chat, browsing) runs side by side.

How boards join

Flash another board, put it on the same network, and it finds the others by itself (mDNS service _axisbbs._tcp plus UDP broadcast). There is nothing to configure.

  • The SD board is main and node 1. The board with the SD card is the main: it owns the files, messages and lists, and serves them to the others over the link. A main without a card hands the role to a board that has one as soon as it joins. More boards with cards add their cards to the file areas; see SD card clustering.
  • One set of settings. Every other board takes the main's settings over the link, keeping only its own board_name, sessions and telnet_port. A change on the main (from @SET or the THEME button) reaches every board at once.
  • One user base. Every board keeps the whole user base. Changes travel as single records, so a new account or a password change on any board is on all of them a moment later.
  • Node numbers. Each board gets one number per session and keeps it across reboots. Once every node has been idle for 10 seconds (the local console counts as busy), the main renumbers the cluster so its own sessions are 1, 2 and so on, then each other board in order, closing gaps like "2+4".
  • Failover. Boards trade a heartbeat every second. If the main goes away, the next board takes over within about 5 seconds; the board with the SD card always wins the main role back.
  • Caller relay. Callers dial the main. When every node on the main is busy, it passes the caller to the lowest free node on another board, passing the bytes both ways untouched.
  • Doors on other boards. A board without the door files runs the door locally and reads the main's door folder over the link, with the main's record locks, so a multinode door like LORD keeps its data whole.
SD card clustering (pool and mirror)

Put an SD card in more than one board and the cards work together. There is nothing to set up for the pool; mirroring is one letter per area.

  • Every card adds to one library. The main lists each area across every card in the cluster as one list. A file that is on two cards shows once (the larger copy, if they differ), with the description from whichever card has one. Callers on any board, with or without a card, see the same lists.
  • Uploads go to the roomiest card. A new upload is written to the card with the most free space, its own or another board's, and its FILES.BBS description goes on that card. Downloads read from a card that has the file, the main's own card first.
  • Mirrored areas keep two copies. Add |m to an area line (area3=gcode|G-code and Toolpaths|0|m) and the main copies every file in that area that only one card holds onto a second card with room, in the background: one file at a time, 2 KB per turn of the main loop, so callers never notice. A copy only shows up once it is whole.
  • When a board is down. Its card simply drops out of the lists until it comes back; nothing waits on it longer than a couple of seconds. A file in a mirrored area is still there from its other copy. A copy cut short by a board leaving is thrown away and made again on a later pass. The sysop's remove and rename reach every copy that is up.
  • Checking on it. On the main's serial console, @CARDS lists each card board with its free space and whether it is up, and @MIRROR shows the mirrored areas and what the mirror is doing (copying, resting, how many copied or failed, the last event). Mirror copies also go in the event log ("mirror: copied X to node 2").

With one SD card in the cluster (the usual setup) everything works exactly as before: the main's card is the library.

SD disc changer (work in progress)
Work in progressDesigned and planned on 2026-11-04, not built yet. This is how the SD cards will work by default; pool and mirror (above) becomes a build option, AXIS_SD_POOL.

Every SD card becomes a disc in a CD-ROM changer, the way a Night Owl shareware CD worked on a 90s board. Swap cards and the file areas follow.

  • A card is a disc. Only the card's /files folder is the disc; each subfolder with files in it is one area, named after the disc (NIGHTOWL 12: Games). The disc name is the card's volume label. The rest of the card stays free for anything else.
  • Hot swap. Pull a card out of any board or push one in and, within a few seconds, every node gains or loses that disc's areas, with a DISC IN or DISC OUT toast on the screens and a notice to callers online. A blank card does nothing until files show up in its /files.
  • FILE_ID.DIZ built in. A file with no description gets one from the FILE_ID.DIZ inside its archive, read once when the disc goes in and saved with the disc. A FILES.BBS description wins.
  • Never merged. The same folder on two discs is two areas.
  • The main's card too. Its message bases and doors will be backed up on another board's card, so pulling it keeps the BBS running from the backup; uploads land on the backup meanwhile and are combined back when the card returns. The main stays main.

Teleconference

Paging the sysop

P (or Y) asks for a one-line message for the sysop. It shows as PAGE on every CYD's activity screen for a minute, sets the PAGE light and the magenta LED strobe, and goes in the event log.

The MultiNode menu

N at the main menu (= with the O/2 letters) opens the Oblivion/2 style multinode commands. They work across boards.

  • B broadcast to every node

  • W who's online

The 8086 door runtime and adding doors with doorN.

D lists the doors, numbered 1 to 9, then A, B, C and on. Type a door's key to go in; Enter goes back to the menu. When the door ends, the caller comes back to the BBS, with a note if the door ran out of memory, ran out of time, or could not start.

The DOS door runtime

Real DOS door games run on the ESP32 itself. The runtime is an 8086 CPU emulator (a refactored FabGL core) with paged memory, a high-level DOS, a BIOS, and a FOSSIL driver on INT 14h that connects the door's serial port to the caller's telnet line. The door gets a DOOR.SYS (or DORINFO1.DEF) drop file like it would on a 90s BBS.

  • Where the files go. Each door lives in /doors/<id>/ on the board's storage (the SD card if there is one). DOS sees that folder as C:\.
  • Door code in flash. The first time a door runs, its EXE is relocated and written to the door flash partition (448 KB), and served from there afterwards. The partition holds one door at a time and remembers which, so switching doors rebuilds it. @DOORCHECK lord on the serial console does this ahead of time.
  • Memory. The door borrows the board's screen memory and spare instruction RAM as its guest memory. Only one session per board can be in a door at once; a second caller is told the door is busy.
  • Time. A door session is limited to daily_minutes.
  • The CYD's own screen has no terminal for a door: the local console says to call in over telnet for doors and downloads.

A C:\> prompt over a sandbox folder on the SD card (dosbox by default). Nothing of the BBS is reachable from it: .. stops at the sandbox root and there are no other drives. The sandbox can hold up to 16 MB.

Applications, validation, levels, permissions, time limits, twits.

Accounts are kept in internal flash (/users.dat) on every board. Passwords are stored as salted SHA-256 hashes, never as text. A caller gets three tries at a password, then the call ends. Brute-force brake: each wrong password holds the line 2 seconds, then 4, and an address that fails three calls within 10 minutes (wrong passwords, a wrong new user password, or bad logins on the sysop panel port) is turned away for 5 minutes, then 10, 20 and so on up to an hour for a repeat offender. A good login clears it.

The new user application

A caller who types a handle nobody uses is asked whether to apply (in the Oblivion look, Apply on the matrix does the same). The application is about twenty questions in sections, and only the sysop reads the answers:

  • About you: a password (6 or more characters, twice), first name, location, email (optional), how they heard about the board.
  • The shop: do they own a CNC (router, mill, lathe, laser or 3D printer), the machine and controller, what they cut, whether they know someone with one, a rotary (4th) axis.
  • RotatoCAM: do they know it, are they a RotatoCAM Pro user, have they been to rotatocam.com and jmscnc.com, what CAM software they use.
  • The scene: first BBS, best ANSI group, their terminal, what they would upload, why they should be let in.
  • The rules, then review and submit.
Validating callers
  • On the CYD: tap the activity screen, USERS (pending callers are listed first), tap a caller to read every answer, then VALIDATE or DENY.
  • Over telnet: the sysop user editor (*), V or D. Validating raises security to at least 20.
  • On the serial console: @ADDUSER handle|location|password adds a caller who is already validated (security 20, password 6+ characters).
Security levels and permissions
  • Security level (0 to 255). File and message areas can require a level (areaN=id|name|level); callers below it never see the area. 255 is a sysop.
  • Permissions: each caller has files, messages and doors switches, all on by default. A caller with one off is told that part is closed to their account.
  • Free downloads: skips the download gate and the ratio.

On the CYD these are under USERS, a caller, ACCESS: toggles for FILES, MSGS, DOORS, FREE DL and SYSOP. Changes are saved and synced to every board.

Time limits and idle logoff

daily_minutes (default 60) is enforced per call: at 5 minutes left the caller sees a warning, and at zero they are logged off. The Oblivion prompt shows [N left]. A door session gets the same limit. The sysop is exempt. idle_minutes (default 5) logs off a caller who types nothing for that long, including during the application; doors and transfers are not counted as idle.

The twit flag

The quiet way to deal with a problem caller. A twit's message posts are hidden from everyone but them and the sysop, and their oneliners, rumors and teleconference lines reach nobody but them. They are told it all worked. Toggle it with T in the user editor.

Sysop promotion

Any user at security 255 is a sysop: no time limit, every area, and the sysop commands. Promote a caller with @SYSOP handle on the serial console, the SYSOP toggle under ACCESS on the CYD, or security 255 in the user editor.

Every board shows the whole cluster's state on its LED, not just its own. On the CYD that is the RGB LED on the back (GPIO 4, 16 and 17). When several things are going on, each active signal gets a 2 second turn.

The headless LED ring

The headless-ring build drives an eight-light ring (reds on GPIO 23, 19, 12, 25 and greens on 22, 18, 14, 33) as a cluster status ring:

Plain ESP32 boards as extra nodes, set up over AXIS-SETUP.

Any plain ESP32 dev board (no screen, no touch, no SD card) can join the cluster as more nodes. It takes 3 callers by default, since it has no screen to draw.

Optional Discord announcements and dynamic DNS (No-IP or GoDaddy).

Extras that reach out to the internet. Both are off by default, and both are optional: the BBS needs neither.

  • Discord announcements. Scene news goes to a Discord channel webhook: new user applications, validations, accounts added, uploads, oneliners, rumors, door launches and sysop pages. Never calls, addresses or system details. @everyone and @here in caller text are neutralised.
  • No-IP dynamic DNS. Keeps a free No-IP hostname (like myboard.ddns.net) pointed at your home IP. Works with an account login or a DDNS key (update host all.ddnskey.com, which updates every host on the key). Checked every 10 minutes, updated only when the IP changes; the first check waits a minute after boot. If No-IP refuses (bad login, unknown host, abuse) the board stops asking until you set it again, as No-IP requires. The setup wizard asks for it, or set it on the serial console.
  • GoDaddy dynamic DNS. Keeps a GoDaddy subdomain's A record pointed at your home IP, checked every 10 minutes (via api.ipify.org). Handy with port forwarding.

They use HTTPS with real certificate checks (the root certificates are built into the firmware). A TLS handshake needs about 45 KB of free memory, more than a busy CYD main has, so the work is done by whichever board holds these settings, typically a headless node. No-IP is the exception: on a board without room for HTTPS it updates over plain HTTP (No-IP supports it), so it runs fine on the main. The board only tries HTTPS when the memory is there. Every board's news travels to the main and out over the link to that board. The secrets live in that board's own NVS, set on its serial console, and never go into /axis.ini or the cluster settings.

Answers to the usual problems.

My computer can't find axis.local

Some systems do not resolve mDNS names. Dial the board's IP address instead: it is on the activity screen ticker and in SYSTEM on the sysop menu.

The art looks torn or shifted

Set your terminal to 80x25 with a CP437 font and let it wrap at column 80. SyncTERM is the reference. A Windows console telnet client is not a BBS terminal.

The board won't join my WiFi

The ESP32 only sees 2.4 GHz networks. Check the password (SHOW reveals it on the keyboard), move the board closer, or use HIDDEN for a network that does not broadcast. @WIFIPICK reopens the picker.

The file areas say they are offline

The main board has no working SD card. Use a FAT32 card, reseat it and send @SDCHECK, or format it from SYSTEM, FORMAT SD.

A caller can't download anything

That is the download gate: they need to upload something first, or you turn on FREE DL for them. If they have uploaded, check the ratio and free_kb settings.

"The door is busy"

Another caller on the same board is in a door or a transfer; each board runs one at a time. Try again in a bit, or add a board so callers spread out.

The DOS Prompt says it is not enabled

Set its password on the serial console: @DOSPASS yourpassword.

LORD takes a while to start

It is a real DOS program on an emulated 8086 inside a microcontroller. The first run also writes the relocated EXE to flash; @DOORCHECK lord does that ahead of time.

A second board doesn't join

Both boards must be on the same network and subnet, and the router must pass UDP broadcast and mDNS between them. Guest networks with client isolation block it. @NODES shows what each board sees.

I forgot the sysop password

@RESETSETUP on the serial console erases the settings and restarts into the first-boot setup, where you set a new sysop account. User accounts are kept. If another account is a sysop (security 255), it can still log in meanwhile.

Discord or dynamic DNS does nothing

Both are off until set, and the HTTPS work needs about 45 KB of free memory. Set them on a headless node, then check with @WEB and @WEBPING.
